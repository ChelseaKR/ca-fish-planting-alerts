# i18n status: Applies — deferred to the owner's Spanish-scope decision (#6)

Reason: INTERNATIONALIZATION-STANDARD §1 allows N/A only when all three of
its out-of-scope conditions hold. Two fail here. The site and the app show
natural-language text to the public, not only to a developer (condition a).
Both also show dates to anglers, such as "week of September 13, 2026"
(condition c). So the standard applies. Both surfaces are English-only
today, and whether and when to add Spanish is the owner's decision,
tracked in #6.

## Current state

- Site: every page renders `<html lang="en">` from
  `pipeline/src/cfpa/templates/base.html.jinja`. The strings are inline in
  the Jinja templates and in `pipeline/src/cfpa/site.py`, with no catalog.
  Dates are formatted in English by `site.py` (`%B %-d, %Y`) and by the
  `.ics` feeds.
- iOS app: `CFBundleDevelopmentRegion` is `en`, and the Xcode project's
  known regions are `en` and `Base`. The SwiftUI views use string literals,
  with no `Localizable.xcstrings` catalog yet.
- Android app: the Compose screens use string literals, as the iOS views
  do; only the app name, the widget's name and description and the
  notification channel's words are in `android/app/src/main/res/values/strings.xml`.
  The words shared with iOS (the introduction, alerts, freshness, the
  widget) are constants in `android/core`, where tests hold them to the
  same rules. American English only, no `values-es`.
- The snapshot contract (`schema/snapshot.v1.json`) carries CDFW's own
  water and species names, which are English proper names from the source.
  It carries no UI strings.

## Entry point if this changes

- Site: extract the template and `site.py` strings into gettext catalogs
  (`_()` via Jinja's i18n extension) and render one tree per locale with the
  right `lang` on each page. Then this standard's AUTO-GATEs apply: key
  parity, `lang` validity, placeholder parity.
- App: move the view strings into a String Catalog (`Localizable.xcstrings`)
  and add `es` to the project's known regions.
- Android app: move the screen strings into `res/values/strings.xml` and
  add `res/values-es/strings.xml`; move the `core` copy behind the same
  resources or a locale-keyed table.

See `docs/standards/INTERNATIONALIZATION-STANDARD.md` §3.
